# Components

For details on what components are, please see the component section of the [repository file structure document](RepositoryFileStructure.md).

COHO's components are all generated from [ROBOT templates](http://robot.obolibrary.org/template), the tables in `src/templates`. They are listed under `components` in `owlmake.yaml`:

```
components:
  products:
  - filename: GWAS.owl
    use_template: true
    template_options: '--prefix "COHO: http://www.ebi.ac.uk/coho/COHO_" ...'
    templates:
    - GWAS.csv
```

`template_options` gives the prefixes the templates' CURIEs are written with (`COHO:`, `dbpedia:`, `RO:`, `oio:`).

## Editing a component

Never edit the files in `src/ontology/components`: they are rebuilt from the templates. Instead:

1. Edit the template in `src/templates` (for example `src/templates/GWAS.csv`)
2. Rebuild the components:
   ```
   om make recreate-components
   ```
3. Run the [quality control checks](QualityControl.md): `om make test IMP=false`
4. Commit the template and the rebuilt component together

## Curation files

`src/templates` holds only ROBOT templates. The evidence and curatorial decisions the generated templates are built from live in `src/curation`: an `_evidence.tsv` per topic (the reviewed evidence, one row per cohort) and a `_curated.tsv` (hand overrides, which win). Edit the curated files, never the generated templates.

The source tables the reviews were made against are there too: `ega_studies.tsv` and `ega_study_cohorts.tsv` (EGA), `gwas_catalog_cohorts.tsv.gz` (GWAS Catalog), and `new_cohorts_ega.tsv` (cohort names that came up in the EGA review and are not yet in COHO, with any consortium or parent cohort noted; `new_cohorts_ega_check.tsv` is their match against the list COHO was seeded from). Refreshing a source means replacing its table and re-running the scripts.

## Example studies

Each cohort is linked to one study that used it, as an `example of usage` (IAO:0000112) annotation holding the study's accession (an EGA `EGAS…` or GWAS Catalog `GCST…`), with the study's publication as a `PMID:` xref on the annotation and a title as `dcterms:title` on it (the paper's, or the EGA study's own where it has no paper), which is what OLS shows beside the accession. Where a reviewer's evidence that the study used the cohort was verified against its source, the quote and the source URL are also on the annotation, as `rdfs:comment` and a second `oboInOwl:hasDbXref`. These come from the `example_studies.owl` component, whose template, `src/templates/example_studies.tsv`, is itself generated and should not be edited by hand:

```
src/scripts/example_studies.py
```

Paper titles are looked up in Europe PMC and kept in `src/curation/example_studies_titles.tsv`. It reads, from `src/curation`, the EGA studies a human reviewed for cohort mentions (`ega_studies.tsv`, with their verified matches in `ega_study_cohorts.tsv`) and the GWAS Catalog's studies with one cohort per line (`gwas_catalog_cohorts.tsv.gz`, a Catalog export of 2026-09). How a study is chosen is described at the top of the script.

Cohorts the script finds no study for are printed, some with a candidate study that matched on an acronym alone and needs a curator to confirm it. To give a cohort an example by hand, or to overrule the script's choice, add a line to `src/curation/example_studies_curated.tsv` (tab-separated columns `ID`, `example study`, `PMID`, `note`) and run the script again. A line with a PMID and no accession gives the paper itself as the example. A line with both left empty rejects the script's choice without replacing it: acronyms are shared between cohorts (the GWAS Catalog's `ACP` on GCST90281184 is an Amish cohort, not the Asian Cancer Project), so a match on one is not always right. The current curated rows come from two reviews of every cohort on 2026-09-22, merged into `src/curation/example_studies_evidence.tsv` (one row per cohort: verdict, accession, PMID, evidence quote, source URL, whether the quote was verified, confidence, and the reviewer's remark); accessions, PMIDs and quotes were checked against Europe PMC, PMC, the GWAS Catalog and EGA before being accepted.

## Data collection locations

Where a cohort's participants were recruited is asserted with `has_data_collection_location`, to a country or region from the `gaz_xrefs.owl` component, by the `locations.owl` component. Its template, `src/templates/locations.tsv`, is generated by `src/scripts/locations.py` from `src/curation/location_evidence.tsv` (a review of every assertion, one row per cohort with the countries asserted, a verdict, the right countries, the evidence and whether its quote was verified) and `src/curation/location_curated.tsv` (overrides: `ID`, `countries` as pipe-separated dbpedia resource names, `quote`, `URL`, `note`; an empty `countries` removes the cohort's locations). Where the evidence quote was verified in its source, it goes on the assertion as `rdfs:comment`, with the source URL as `oboInOwl:hasDbXref`. The location is where participants were recruited, not where the data were analysed or are held. A country the review needs that `gaz_xrefs.tsv` lacks must be added there first, with its GAZ xref and continent; the script refuses to run otherwise.

## Definitions

Each cohort's textual definition (`IAO:0000115`) comes from the `definitions.owl` component, generated by `src/scripts/definitions.py` from `src/curation/definitions_evidence.tsv` (one row per cohort: the definition, its source, a supporting quote and whether the quote was found in the source) and `src/curation/definitions_curated.tsv` (overrides; an empty definition withholds one). Each definition carries its source as `IAO:0000119` (the paper's PMID, or the URL of the cohort's own site) and, as `dcterms:contributor`, the agents that drafted and checked it: the definitions were written by an AI model from sources it retrieved and checked by another against those sources, and the annotations say so on every one. `src/curation/type_changes.tsv` lists the cohorts whose type (cohort or cohort aggregation) the drafting suggested changing, and which were applied.

## Adding a component

1. Create the template, `src/templates/your-component-name.tsv` (or `.csv`)
2. Add the component to the `components` list in `owlmake.yaml`, as above
3. Bring the repository into step with `owlmake.yaml`:
   ```
   om update-repo
   ```
   This adds the component to the imports of the edit file (`src/ontology/coho-edit.owl`), tells the XML catalog (`src/ontology/catalog-v001.xml`) where its IRI is to be found, so that Protégé and the build can load it, and creates a placeholder `src/ontology/components/your-component-name.owl`.
4. Build it: `om make recreate-components`

Removing a component is the same in reverse: take it out of `owlmake.yaml`, run `om update-repo`, and delete its file.

A component can also be derived from SSSOM mappings (`use_mappings: true` with a list of `mappings`) or fetched from a remote resource (`source: https://example.org/component-source.owl`). One that is generated by a process of its own is described as a target, see [Build configuration](BuildConfiguration.md#building-something-in-a-way-of-your-own).
